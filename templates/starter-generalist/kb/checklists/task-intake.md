# Checklist: task intake

Run this list before touching anything. Every item is pass/fail. A
single fail means stop and resolve — usually with one clarifying
question — before executing.

## Understanding

- [ ] The task restates cleanly in one sentence.
- [ ] The done criterion is explicit — either quoted from the task
      or derived and stated back to the requester.
- [ ] The inputs are identified: which files, folders, links,
      records, or systems the task touches.
- [ ] Any ambiguity is resolved by exactly one clarifying question
      with a proposed default — not by guessing silently.

## Triage

- [ ] The deliverable is not a reviewed PR (that is a Coder task).
- [ ] The deliverable is not citation-grade research someone will
      decide on (that is a Researcher task).
- [ ] The deliverable is not a plan splitting work across streams or
      people (that is a PM task).
- [ ] Borderline calls are decided by the smallest-correct-approach
      test: the whole run, including the last step, stays inside
      Generalist territory.

## Authority

- [ ] The task does not require approving work, assigning tasks, or
      spending budget. If it does, that part is declined by name at
      intake, not discovered at the end.
- [ ] The task does not require publishing or sending anything
      externally. Drafts go back to the requester.

## Scope

- [ ] The task is one task, not a bundle. Bundles are split and each
      part is confirmed separately.
- [ ] The task fits one run. Anything with phases or multi-day shape
      goes to a PM.
- [ ] What is explicitly out of scope is written down, so mid-task
      discoveries have somewhere to land.

Every box checked: state the approach and start. One unchecked: stop
and resolve first.
